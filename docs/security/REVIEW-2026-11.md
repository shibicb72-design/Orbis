# Orbis security and privacy review, November 2026

Reviewed: `origin/main` at `a07b0fe` (0.5.1, versionCode 18). Read-only review of the Kotlin sources, manifest, built-in
extensions, Gradle and CI files. No code changed. "Proven by reading code" means the path was traced in the source;
"needs emulator proof" means the code says so but the behaviour was not observed live.

Scope follows the owner's list: entry points, web-to-app boundary, private browsing, local data, LAN/network (Cast,
DLNA, suggestions), build and release. Earlier reviewed areas (passwords screen, app links, address bar display, supply
chain) were re-read only where new code touches them.

## Findings

### S-01 (medium) Chromecast TLS trusts any certificate

- File: `app/src/main/java/com/shibi/orbis/cast/ChromecastHub.kt:287-307` (`openCastSocket`), `:383-393` (`LanCastTrust`).
- What: `LanCastTrust.checkServerTrusted` only checks the chain is non-empty. The socket is opened to whatever
  address mDNS announced for `_googlecast._tcp` (`ChromecastDiscovery.kt:150-164`), with only an "is a private LAN
  address" check. There is no device-auth challenge and no pinning.
- Attacker: a device on the same Wi-Fi (guest, IoT box, another phone). It answers mDNS with the real TV's friendly
  name (`fn`) and id, or simply ARP/mDNS-races the TV, and receives everything Orbis sends over the Cast channel:
  the media URL (often a signed, time-limited URL that grants playback), title, poster URL, YouTube video id and
  position. For a private tab the title is replaced (`CastCoordinator.kt:312-319`) but the media URL still goes out.
- Why medium and not high: LAN attacker only, user must press Cast, data is one page's media address.
- Fix (coder):
  1. Trust-on-first-use pinning, no SDK: in `LanCastTrust`, compute SHA-256 of `chain[0].encoded`; look up the
     device's stored pin by `ChromecastDevice.id` in a small `SharedPreferences` file `cast_pins`; if none, store it;
     if different, throw `CertificateException`. `openCastSocket` returns null, `ChromecastHub.cast` reports a new
     `CastFailure.UNTRUSTED` and the sheet shows "This device's certificate changed. Cast anyway?" with a Forget
     button that drops the pin. Pass `device.id` into `openCastSocket`.
  2. Stronger option (OWNER DECISION, more work): verify the device certificate against Google's Cast root CAs
     (PEM bundle from Chromium `openscreen/cast/common/certificate`) and run the `urn:x-cast:com.google.cast.tp.deviceauth`
     challenge. No Cast SDK or Play Services is needed, but the CA bundle has to be maintained.
- Proof: unit test for the pin logic (make the trust manager `internal`, feed two different self-signed certs for
  the same id, expect the second to throw). Emulator: not reproducible without a LAN peer; a desktop `openssl s_server
  -port 8009` on the same network plus a spoofed mDNS record (`avahi-publish -s FakeTV _googlecast._tcp 8009 fn=TV`)
  shows Orbis connecting and sending CONNECT/GET_STATUS before the fix, refusing after.
- Trade-off: none for option 1 (first connection unchanged). Option 2 changes behaviour on unofficial receivers.

### S-02 (medium) A transient Keystore error sets the login file aside

- File: `app/src/main/java/com/shibi/orbis/passwords/LoginStore.kt:75-93`, `storage/AtomicTextFile.kt:39-52`,
  `passwords/LoginManager.kt:50-67`.
- What: `FileLoginStore.load` catches every `Exception`. `AEADBadTagException` or a JSON error (a truly corrupt file)
  is the intended case, but `KeyStoreException`, `ProviderException`, `UnrecoverableKeyException`, `IllegalStateException`
  and StrongBox "busy" errors from `Cipher.init`/`doFinal` are transient and also land here. The file is renamed to
  `logins.enc.corrupt`, `LoginManager` sets `loaded = true` with an empty list, autofill offers nothing, and the next
  `save` writes a fresh file. There is no UI to restore `.corrupt`; `save(emptyList())` (Clear passwords) deletes it.
- Attacker: none directly; this is data loss of all saved passwords after a one-off Keystore hiccup. Security-adjacent
  because the orphaned `.corrupt` file keeps the ciphertext around after the user thinks they cleared passwords
  (only when the aside happened for a transient reason; a real clear deletes it).
- Fix (coder):
  - In `FileLoginStore.load`, only call `setAside()` for `javax.crypto.AEADBadTagException`, `IllegalArgumentException`
    (Base64), `org.json.JSONException` and the `require` failure. For any other exception: do not touch the file, set
    `blocked = true`, rethrow so `LoginManager.load` logs `logins load failed: <class>` and keeps `loaded = false`
    (today it sets `loaded = true`; change it to leave `loaded` false and schedule one retry, e.g. on next
    `MainActivity.onStart`).
  - `LoginManager.clearAll` should only `deleteAside()` when the aside was created by a decode failure in this process
    (keep a flag), not unconditionally.
- Proof: unit test with a `LoginCrypto` stub that throws `java.security.KeyStoreException` once: the file still
  exists, `save` throws, second `load` succeeds. Existing `PasswordsTest` covers the corrupt-file path.

### S-03 (medium) Private download names outlive the private session in notifications

- File: `downloads/DownloadNotifications.kt:72-91` (`postResult` uses `entry.fileName`), `DownloadNotificationModel.kt:36-38`
  (single ongoing download shows its name), `DownloadManager.kt:270-280` (`forgetPrivate` returns ids but nobody cancels
  their notifications), `OrbisApp.kt:188-193`.
- What: the list hides private downloads when the last private tab closes, but the "Download complete: <name>"
  notification stays in the shade, and the ongoing notification shows the private file name while it runs.
  `VISIBILITY_PRIVATE` keeps it off the lock screen only.
- Attacker: someone holding the unlocked phone after the user left private browsing.
- Fix (coder): in `OrbisApp` `onPrivateBrowsingEnded`, call `DownloadNotifications.cancelResults(this, downloads.forgetPrivate())`;
  in `DownloadManager.finish`, when `dropOnFinish` removes an id, expose it (callback or flow) so its result
  notification is cancelled too. In `DownloadNotificationModel.from`, use `null` name for a private single download
  (string "Private download") and in `postResult` use the generic text when `entry.isPrivate`.
- Proof: emulator: open a private tab, download a small file from the test server (`Content-Disposition:
  attachment; filename=secret-report.pdf`), close the private tab, pull down the shade. Before: the name is shown.
  After: no result notification; ongoing one says "Private download". Unit test on `DownloadNotificationModel.from`.
- Trade-off: owner earlier accepted that private download *files* are kept (R2303-10). This only touches notifications.

### S-04 (low) Device-to-device transfer is not excluded

- File: `app/src/main/AndroidManifest.xml:120` (`android:allowBackup="false"`, no `dataExtractionRules`).
- What: Android documents that on Android 12+ `allowBackup=false` blocks cloud and adb backups but D2D migration still
  copies app data unless `dataExtractionRules` has a `<device-transfer>` section
  ([Auto Backup docs](https://developer.android.com/identity/data/autobackup),
  [backup best practices](https://developer.android.com/privacy-and-security/risks/backup-best-practices)). So a
  phone-to-phone transfer copies history, bookmarks, tabs (with Gecko session state), site permissions, the debug log,
  `youtube_ad_savings.json`, `privacy_stats.json` and `logins.enc` (unreadable without the old Keystore key, which then
  triggers S-02's aside path on the new phone).
- Attacker: whoever ends up with the target device of a transfer; also simply unexpected for a privacy browser.
- Fix (coder): add `res/xml/data_extraction_rules.xml` with `<cloud-backup>` and `<device-transfer>` both excluding
  `domain="file"`, `"sharedpref"`, `"database"`, `"external"` (path `.`), and `android:dataExtractionRules="@xml/data_extraction_rules"`
  with `tools:targetApi="s"` on `<application>`. OWNER DECISION: if the owner wants bookmarks and settings to move to a
  new phone, exclude only `logins/`, `history/`, `tabs/`, `debug_log.txt`, `site_permissions.json`, `youtube_ad_savings.json`.
- Proof: `aapt2 dump xmltree` on the built APK shows the attribute; lint check `DataExtractionRules` passes.

### S-05 (low) DLNA control URL and redirects may target other LAN hosts

- File: `cast/DlnaMessages.kt:119-130` (`resolveControlUrl` accepts any http URL), `cast/LanHttp.kt:39-50`
  (`redirectTarget` accepts any LAN address), `:96-121` (`localTarget` resolves host names).
- What: discovery only fetches a description from the SSDP packet's own source address (good,
  `selectDiscoveryTargets`), but the `controlURL` inside that description can name a different LAN host and port, e.g.
  `http://192.168.1.1/...`. Orbis then POSTs fixed SOAP bodies (Stop, SetAVTransportURI with the media URL, Play) there
  with `Content-Type: text/xml` and a `SOAPAction` header. A host name in the control URL also causes a DNS lookup.
- Attacker: a device on the LAN. Impact is limited (fixed body, no response shown), so low.
- Fix (coder): in `resolveControlUrl`, require `URI(resolved).host` to equal `URI(locationUrl).host` and be an IP
  literal; in `redirectTarget`, require the same host as `currentUrl`. Both are pure functions with tests in `DlnaTest`.
- Proof: unit tests (`resolveControlUrl("http://10.0.0.5:49152/desc.xml", "http://10.0.0.1/ctl")` returns null).

### S-06 (low) Download resume does not check the resource is unchanged

- File: `downloads/DownloadManager.kt:180-206, 304-307`, `engine/GeckoEngineImpl.kt:333-363` (`fetchFrom`).
- What: resume sends `Range: bytes=N-` and appends when `Content-Range` starts at N. No `If-Range`/`ETag`/`Last-Modified`
  check, so a resource that changed between pause and resume yields a spliced file. Attacker is the server itself or
  a network party for plain `http://` downloads (HTTPS-only off by default in normal tabs).
- Fix (coder): record `ETag`/`Last-Modified` from the first response in `Paused`; send `If-Range` with it; if the
  response is 200 (not 206) or the validator differs, restart from byte 0 (already the fallback when offsets differ).
- Proof: unit test in `DownloadManagerTest` with a fake `fetchFrom` returning 200 after a pause: the part file is
  rewritten from 0, not appended.

### S-07 (low) Private voice search can still leave the phone

- File: `ui/browser/VoiceSearch.kt:38-48`.
- What: `EXTRA_PREFER_OFFLINE` is advisory; the recognizer (Google, Samsung) may still upload audio and keep the query
  under the user's Google account. Not Orbis's data, but a private-tab expectation.
- Fix: OWNER DECISION. Either hide the microphone button in private tabs (`onVoice = null` when `selectedTab.isPrivate`,
  `BrowserScreen.kt:839,1039`) or show a one-time note. No code risk either way.

### S-08 (low) Exception messages in the debug log

- File: `engine/GeckoEngineImpl.kt:1233` (`reopen after $kind failed: ${it.message}`), `:2289` (`close failed: ${it.message}`),
  `OrbisApp.kt:348` (`engine warmUp failed: ${it.message}`).
- What: the project rule is "exception class only" (kept everywhere else). Gecko messages are unlikely to carry a URL,
  but the rule exists so the log can be copied to the clipboard safely (`DebugLogScreen.kt:72-76`).
- Fix: use `it.javaClass.simpleName` in the three places. Grep `\.message}` in `app/src/main` to confirm no others.

### S-09 (low, suspected) Imported HTML can redirect to the web without a tap

- File: `engine/ImportedDocuments.kt:66-69` (CSP), `engine/GeckoEngineImpl.kt:701-743` (`onLoadRequest`).
- What: the import CSP blocks scripts, subresources, frames and forms, but CSP has no control over
  `<meta http-equiv="refresh" content="0;url=https://evil.example/login">`. A shared "invoice.html" would open and
  immediately navigate the tab to a phishing page, with the address bar then showing that site. Same outcome as sharing
  a link, so low; listed because the import feature's own threat model is "a file from a stranger".
- Fix (coder): in `onLoadRequest`, when the committed URL (`_state.value.url`) is an import (`isImportLoadUrl`) and
  `!request.hasUserGesture` and the target is a web URL, return DENY and log `"import auto-navigation blocked"`. Links
  tapped in the file keep working.
- Proof (emulator): share an HTML file containing only the meta refresh from the test server page's "share as file"
  helper (or `adb shell am start -a android.intent.action.SEND -t text/html --eu android.intent.extra.STREAM content://...`
  from a small provider). Before the fix the tab lands on the target URL; after, it stays on the file.

## Checked and fine

Entry points
- Exported components: `MainActivity` (launcher, `content:` PDF/HTML VIEW and SEND only, no BROWSABLE), `LinkRouterActivity`
  (http/https only, rebuilds a clean intent, `externalUrlFrom` caps length and refuses control characters),
  `OrbisCustomTabsService` (warmup only; no postMessage, relationship validation, receiveFile or extraCommand).
  `CustomTabActivity`, widget receiver, `CastActionReceiver`, services and the FileProvider are not exported.
- Custom Tabs: only toolbar colour and title flag are read from the caller (`CustomTabIntents.kt`), host shown from the
  committed URL, lock icon only for https, popups become normal Orbis tabs with a gesture, downloads prompt as in a tab.
- Shared PDF/HTML: `content:` only, own-provider refused (including `0@authority` forms), 64 MB cap, idle and overall
  timeouts, names sanitised, random directory, UTF-8 validated, CSP meta inserted after BOM/comments/doctype by a
  tokenizer, NUL/UTF-16 refused, `file:` subframes denied, JavaScript forced off for HTML and restored for web pages,
  files deleted after 24 h, with history and with cache. Very thorough (`ImportedDocuments.kt`, `SharedDocumentOpen.kt`).
- `intent:`/`market:`/`magnet:` and app schemes: component, selector, extras, flags and clip stripped; own package blocked;
  `file:`/`content:` data blocked; tap or recent-tap redirect required; one prompt at a time (`ExternalApps.kt`,
  `GeckoEngineImpl.kt:891-968`).
- QR: only explicit http(s) opens; everything else is text (`QrDecode.kt`). Voice result goes through the address-bar
  normaliser. Drag and drop and widget use the same normaliser; only http(s) is ever loaded (`UrlInput.kt`).
- Home shortcuts: SHA-256 ids, explicit component, http(s) only.

Web to app
- Popups need a user gesture, http(s) target and a ready tab list; `onNewSession` re-checks.
- Auth prompt skips cross-origin subresource challenges and names the receiving host. Dialog spam guard on prompts and
  permission requests. File picker copies `content:` into a private cache, never hands `file:` picks to pages; camera
  temp is random-named and deleted.
- Downloads: `DownloadFileNames` handles `filename*`, traversal, bidi/format characters, reserved names, length;
  `isInside` re-checked before every write; length mismatch fails the download; FileProvider roots limited to the two
  download dirs and the camera temp dir; MediaStore copy only for non-private completed files.
- Gecko settings: `aboutConfigEnabled(false)`, remote debugging left at its default (off), ETP strict, Safe Browsing on,
  cookies isolated, HTTPS-only on for private tabs (off for normal tabs by owner choice), `usesCleartextTraffic=false`.
- Built-in extensions: reader and cast only `connectNative` to the app and read the page; darken is CSS only; yt-ads is
  `incognito: not_allowed`, writes response bodies back unchanged, hosts limited to YouTube and ad domains. Note for the
  owner: the yt-ads estimate stores YouTube video ids and titles in `youtube_ad_savings.json` (cleared with history,
  documented in code). uBO install: AMO https URL, exact id, `SIGNED` state required, data-collection permission denied,
  updates asking for new permissions denied.

Private browsing
- Private tabs are never persisted or in recently-closed; thumbnails are memory only; FLAG_SECURE and no Recents
  snapshot while any private tab or the passwords screen is open; `PrivateImeScope`; no remote suggestions; no login
  save offer; separate Gecko context id rotated and cleared when the last private tab closes; private uploads deleted
  on close; media and cast notifications show a generic title; downloads index never stores private entries; stats
  count but do not record hosts from private tabs; Custom Tabs always use the normal profile (as Chrome does).

Local data
- Logins: AES-256-GCM, Keystore key, random IV, atomic file replace; passwords screen was reviewed earlier.
- No `Log.*` calls, no world-readable modes, no secrets in the debug log beyond S-08; the log is 500 lines max.
- Update checker removed; its prefs are deleted at start. No backend, no accounts.

Network
- Search suggestions: https endpoints, no cookies, 2.5 s timeout, 32 KB cap, generic User-Agent, normal tabs only.
- CASTV2 framing: 256 KB cap, varint bounds, body deadline; JSON parsed with `opt*`; silence timeout.
- SSDP: 200 replies only, 16 KB cap, LOCATION host must equal the packet source and be a LAN IP; description XML
  refuses DOCTYPE/ENTITY before parsing, entity resolver stubbed, 512 KB cap. LAN HTTP client: raw socket bound to
  Wi-Fi/Ethernet, LAN addresses only, one redirect, 512 KB response cap, chunked decoding bounded.
- Cast of a page from a private tab: media URL goes to the chosen device only, never to disk. YouTube casting now also
  contacts YouTube's lounge servers with the video id (no cookies); the owner accepted this on 2026-11-10.

Build and release
- Release: R8 on, not debuggable, upload key read from outside the repo (`ORBIS_SIGNING_PROPERTIES` or owner folder),
  unsigned on CI. `debug.keystore` is the documented debug-only key. Dependency verification (SHA-256) on, Gradle wrapper
  checksum set, CI actions SHA-pinned, `permissions: contents: read`, no secrets used. Permissions declared match use;
  `QUERY_ALL_PACKAGES` removed; foreground service types declared; `NEARBY_WIFI_DEVICES` is `neverForLocation`.
- Dependency versions are the 2026-11 stable pairs (GeckoView/AC 159, AGP 9.4, Kotlin 2.4.10); no known-CVE versions
  were identifiable from the catalogue at review time.

Not verified (out of reach without a device): actual Gecko behaviour for meta refresh from `file:` with JavaScript
off (S-09), and whether `clearDataFromBaseDomain` accepts a subdomain argument in GeckoView 159
(`GeckoEngineImpl.kt:365-396`; functional, not security).
